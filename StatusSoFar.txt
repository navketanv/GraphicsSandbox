## ScopedBinder

Generic RAII helper.

Concept:

template
concept Bindable = requires(const T& obj)
{
{ obj.bind() } noexcept;
{ obj.unbind() } noexcept;
};

Usage:

ScopedBinder vao(m\_vertexArray);
ScopedBinder buffer(m\_vertexBuffer);

Automatically binds on construction and unbinds on destruction.

bind()/unbind() are intentionally public.

## ScopeGuard

Generic cleanup utility.

template\<std::invocable Cleanup>
class ScopeGuard

Stores cleanup callable by value.

Deduction guide:

template
ScopeGuard(T&&) -> ScopeGuard\<std::remove\_cvref\_t>;

Used inside Shader::createProgram() to guarantee shader cleanup.

```text
TriangleGeometry::vertexLayout() is defined in TriangleGeometry.cpp:

GPU::VertexLayout TriangleGeometry::vertexLayout()
{
    GPU::VertexLayout layout{};
    const std::size_t positionOffset = 0;
    const std::size_t colorOffset =
        positionComponentCount() *
        GPU::sizeOf(GPU::VertexAttributeType::eFloat);

    layout.addAttribute(
        0,
        positionComponentCount(),
        positionOffset,
        GPU::VertexAttributeType::eFloat,
        false
    );

    layout.addAttribute(
        1,
        colorComponentCount(),
        colorOffset,
        GPU::VertexAttributeType::eFloat,
        false
    );

    return layout;
}

We decided to keep the declaration in the header and the definition in .cpp rather than inline, because TriangleGeometry may grow and we want to avoid making the header unmanageable.

- vec1 -> 1
- vec2 -> 2
- vec3 -> 3
- vec4 -> 4
It does NOT mean number of vertices/objects to draw.

GPU::Vertex{}.m_color.size()

VertexArray::attachIndexBuffer() was:

ScopedBinder<VertexArray> vao(*this);
ScopedBinder<Buffer> bufferObj(buffer);

This is important:
An element/index buffer binding IS VAO state in OpenGL 3.3+ core. Therefore the EBO must be bound while the correct VAO is bound, and it must remain associated with that VAO after the function exits.

Using ScopedBinder<Buffer> for the EBO means it gets unbound on scope exit, which may cause the VAO's element-buffer association to become 0 depending on OpenGL semantics/context behavior.

We were discussing changing attachIndexBuffer to bind the index buffer while VAO is bound, but NOT immediately unbind the EBO. The correct pattern is essentially:

ScopedBinder<VertexArray> vao(*this);
buffer.bind();

Because EBO binding belongs to VAO state. It is NOT a resource leak to leave the OpenGL EBO binding associated with the VAO. The Buffer C++ object still owns/deletes the OpenGL buffer handle normally.

This distinction is important:
- OpenGL binding state != resource ownership
- Leaving an EBO associated with a VAO does NOT leak it
- The Buffer destructor deletes the actual GL buffer object
- VAO destruction deletes the VAO object

However, VBO binding via GL_ARRAY_BUFFER is different: glVertexAttribPointer captures the buffer association at the time glVertexAttribPointer is called, so the VBO itself does not need to remain bound afterward.
```

# Graphics Engine — Geometry Refactor Thread Summary

## Current Architecture Direction

The engine is a modern C++20 graphics engine using SDL2 + OpenGL 4.1 Core on macOS. Design priorities include RAII, strong ownership, small interfaces, composition, and a deliberately **weakly typed/flexible geometry system** rather than hard-coded C++ vertex types.

## Main Decision: Geometry Refactor

The current geometry is hard-coded through `TriangleGeometry`. We decided to introduce a generic `MeshData` representation:

```cpp
struct MeshData
{
    std::vector<std::byte> m_vertices;
    std::vector<std::uint32_t> m_indices;
    VertexLayout m_layout;
};
```

`MeshData` is intentionally weakly typed: it stores raw vertex bytes, indices, and the layout describing how those bytes should be interpreted.

Important conceptual distinction:

* `MeshData` = CPU-side geometry payload **plus the format/interpretation contract**
* `VertexLayout` = communication/translation layer between CPU vertex data and GPU vertex format
* `GPU::Mesh` = actual GPU representation/resource
* `GPU::Buffer` / `GPU::VertexArray` = underlying OpenGL resources/state

Therefore, `MeshData` is not considered "pure CPU data" because `VertexLayout` describes the GPU-facing interpretation of the data.

We decided **not** to put `Geometry` under `GPU`, because `MeshData` and procedural geometry generators are not themselves GPU resources.

## VertexLayout

Current `VertexLayout` remains a class because it maintains state/invariants, particularly `m_stride` corresponding to its attributes.

Current conceptual implementation:

```cpp
class VertexLayout
{
public:
    VertexLayout() = default;
    ~VertexLayout() noexcept = default;
    VertexLayout(const VertexLayout& rhs) = default;
    VertexLayout& operator=(const VertexLayout& rhs) = default;
    VertexLayout(VertexLayout&& rhs) = default;
    VertexLayout& operator=(VertexLayout&& rhs) = default;

    template<typename... Args>
        requires(std::constructible_from<GPU::VertexAttribute, Args...>)
    void addAttribute(Args&&... args)
    {
        m_attributes.emplace_back(std::forward<Args>(args)...);
        const GPU::VertexAttribute& attribute = m_attributes.back();
        m_stride += attribute.componentCount() * sizeOf(attribute.type());
    }

    [[nodiscard]]
    constexpr std::size_t stride() const noexcept {
        return m_stride;
    }

    [[nodiscard]]
    constexpr std::span<const GPU::VertexAttribute> attributes() const noexcept {
        return m_attributes;
    }

    void clear() noexcept {
        m_attributes.clear();
        m_stride = 0;
    }

private:
    std::vector<GPU::VertexAttribute> m_attributes{};
    std::size_t m_stride{};
};
```

It currently still uses `GPU::VertexAttribute` and `GPU` utilities. This is acceptable for now because `VertexLayout` is intentionally the communication/translation layer.

## MeshData

`MeshData` should remain a **struct**, not a class.

Reason: it is currently a passive data-transfer/aggregate type without invariants requiring encapsulation. `VertexLayout`, by contrast, has internal state and behavior and therefore remains a class.

Recommended header:

```cpp
#pragma once

#include <cstddef>
#include <cstdint>
#include <vector>

#include "GraphicsCore/Geometry/VertexLayout.h"

{
    std::vector<std::byte> m_vertices;
    std::vector<std::uint32_t> m_indices;
    VertexLayout m_layout;
};

} // namespace GraphicsCore::Geometry
```

Important: explicitly include `<cstdint>` because `std::uint32_t` is used. `<cstddef>` is needed for `std::byte`.

`MeshData.cpp` is **not needed** unless non-trivial out-of-line member functions are added later. For now it should be header-only.

```cmake
include/GraphicsCore/Geometry/MeshData.h
include/Geometry/TriangleGeometry.h
```

However, since `MeshData` currently has no implementation, `src/Geometry/MeshData.cpp` should likely be removed rather than created.

Also note that `TriangleGeometry` currently lives under:

```text
include/Geometry/TriangleGeometry.h
src/TriangleGeometry.cpp
```

This is temporary legacy structure. Eventually it should become a geometry generator such as:

```text
GraphicsCore/Geometry/Triangle.h
```

which produces `Geometry::MeshData`.

## Immediate Next Step

The next planned change is:

**Modify `GPU::Mesh` so its constructor consumes a single `Geometry::MeshData` parameter.**

Conceptually:

```cpp
GPU::Mesh mesh{meshData};
```

instead of passing vertices, indices, and layout separately.

The desired pipeline is:

```text
Geometry generator
      ↓
  MeshData
      ↓
   GPU::Mesh
      ↓
Buffer + VertexArray
      ↓
    OpenGL
```

Do **not** create `Triangle.h` yet. First make the existing triangle work through the new `MeshData → GPU::Mesh` path. Once that compiles and renders correctly, replace the old hard-coded `TriangleGeometry` with a proper `Geometry::Triangle` generator.

## Important Architectural Principle

Keep the distinction:

```text
Geometry
    = data + description of data

GPU
    = actual GPU resources and OpenGL state
```

Do not introduce an OBJ/glTF/model loader yet. First establish the clean `MeshData → GPU::Mesh` boundary. Then procedural geometry (`Triangle`, `Cube`, etc.) can all produce the same `MeshData`, and asset loading can be introduced later without changing `GPU::Mesh`.

# GraphicsSandbox — Current Project Status

**Last consolidated:** 21 August 2026
**Project:** GraphicsSandbox — C++ Graphics Engine
**Purpose of this document:** Canonical project state. Older GraphicsSandbox discussion threads can be deleted after this is saved.

---

## 1. Project Direction

GraphicsSandbox is being developed as a **small, modern C++ graphics engine**, rather than simply as a rendering demo.

The goal is to use the project to build a strong understanding of:

* modern C++
* engine architecture
* CPU-side data representation
* GPU resource representation
* CPU ↔ GPU translation
* graphics API abstractions
* memory/resource ownership
* geometry representation
* rendering architecture
* eventually CUDA/GPU-compute concepts

The architecture should remain reasonably flexible rather than becoming tightly coupled to one specific rendering implementation too early.

A major design principle so far is:

> **Do not prematurely over-engineer the engine, but make the boundaries between concepts explicit.**

---

# 2. Current High-Level Architecture

The project is being separated conceptually into layers.

At the current stage, the important distinction is:

```text
GraphicsSandbox
    |
    | application / scene / rendering usage
    v
GraphicsCore
    |
    +-- Geometry
    |     +-- Vertex
    |     +-- MeshData
    |     +-- VertexLayout
    |     +-- Triangle
    |
    +-- GPU
          +-- GPU-specific representations/resources
```

The exact directory structure is still being refined, but the important architectural boundary is:

### Geometry

Represents geometry as an engine-level concept.

### GPU

Represents how that geometry is eventually communicated to and represented by the graphics API/GPU.

### GraphicsSandbox

Uses the engine rather than defining engine-level geometry itself.

---

# 3. Geometry Refactoring

The project originally had geometry hard-coded directly in the rendering/application side.

The current direction is to move that into reusable engine-side geometry types.

The conceptual transition is:

```text
OLD

GraphicsSandbox
    |
    +-- hard-coded triangle vertices
    +-- hard-coded indices
    +-- rendering setup
```

toward:

```text
GraphicsSandbox
    |
    +-- asks GraphicsCore for Triangle
              |
              v
        MeshData
              |
              v
        GPU upload / rendering
```

The important consequence is that a triangle should become an **engine geometry object/data provider**, rather than simply a collection of OpenGL calls hidden behind another class.

---

# 4. MeshData

The current CPU-side geometry container is conceptually:

```cpp
struct MeshData
{
    std::vector<std::byte> vertices;
    std::vector<std::uint32_t> indices;
    VertexLayout layout;
};
```

The project direction changed from a fixed/static representation toward a **vector-based representation**.

This is intentional because MeshData should eventually be able to represent arbitrary meshes rather than only a triangle with a fixed number of vertices.

The important pieces are:

```text
MeshData
 ├── vertex byte data
 ├── index data
 └── description of vertex layout
```

The underlying vector representation is also being treated as a deliberate part of the design rather than using fixed-size arrays everywhere.

---

# 5. Why std::byte for Vertices?

The engine is deliberately moving toward a relatively weakly typed/raw representation for generic mesh data.

Instead of:

```cpp
std::vector<Vertex>
```

the current direction is:

```cpp
std::vector<std::byte>
```

This allows MeshData to represent different vertex formats.

For example, eventually:

```text
Position
Position + Color
Position + Normal
Position + Normal + UV
Position + Normal + Tangent + UV
...
```

without making MeshData itself dependent on one concrete C++ vertex struct.

This fits the desired engine philosophy:

> MeshData should describe arbitrary GPU-oriented vertex data rather than impose one universal vertex type.

---

# 6. Vertex

A `Vertex` type still exists and is useful for defining/conveniently constructing particular vertex formats.

The current project has been working with something along the lines of:

```cpp
Vertex
{
    m_position
    m_color
    ...
}
```

The important distinction is:

```text
Vertex
    = concrete/convenient vertex representation

MeshData
    = generic mesh representation
```

Therefore MeshData should not necessarily be permanently tied to `Vertex`.

`Vertex` can be used when constructing specific geometry such as a triangle, while MeshData remains generic.

---

# 7. VertexLayout

`VertexLayout` describes how the bytes in MeshData's vertex buffer should be interpreted.

Conceptually:

```text
MeshData.vertices
        |
        | raw bytes
        v
VertexLayout
        |
        | tells GPU/renderer how to interpret them
        v
GPU vertex attributes
```

This is an important architectural boundary.

There was discussion about whether putting `VertexLayout` directly into `MeshData` makes MeshData no longer "pure CPU-side data."

The current conclusion is effectively:

> `VertexLayout` is a useful **translation/description layer between generic CPU geometry data and GPU vertex representation**.

That is acceptable and intentional.

The layout does not mean MeshData itself becomes an OpenGL object.

---

# 8. Geometry Folder

The current proposed organization is to have a dedicated Geometry area under GraphicsCore.

Conceptually:

```text
GraphicsCore/
    Geometry/
        VertexLayout.h
        MeshData.h
        Triangle.h
        Vertex.h
```

The exact final path/name can still be adjusted, but the important idea is that these concepts belong together.

The previous discussion specifically considered whether MeshData belongs under:

```text
GraphicsCore/Geometry/
```

versus:

```text
GraphicsCore/GPU/Geometry/
```

The preferred direction is to keep **MeshData/Vertex/VertexLayout/Triangle as engine Geometry concepts**, rather than hiding them under a GPU implementation folder.

GPU-specific objects should live on the GPU side.

---

# 9. Triangle

The current design is moving toward a `Triangle` geometry type.

Conceptually:

```cpp
class Triangle
{
public:
    [[nodiscard]]
    static MeshData create();

private:
    ...
};
```

The idea is that:

```cpp
Triangle::create()
```

returns a `MeshData` describing the triangle.

This is preferable to making `Triangle` itself a GPU object.

So:

```text
Triangle
   |
   | creates/describes
   v
MeshData
   |
   | uploaded/translated
   v
GPU resources
```

rather than:

```text
Triangle
   |
   +-- creates OpenGL buffers
   +-- binds VAO
   +-- uploads data
   +-- knows renderer state
```

The latter would couple Geometry directly to the graphics API, which we want to avoid.

---

# 10. Triangle vs TriangleGeometry

There was an explicit discussion around the old/application-side concept:

```text
TriangleGeometry
```

and whether it is effectively becoming:

```text
Triangle
```

The current conceptual answer is:

**Yes, but with an architectural distinction.**

The old `TriangleGeometry` was more closely tied to the rendering/application layer.

The new:

```cpp
GraphicsCore::Geometry::Triangle
```

should represent the **engine-level geometric definition**.

It should not be responsible for OpenGL rendering.

So the evolution is:

```text
Old:

TriangleGeometry
    = geometry + rendering-oriented concerns


New:

Triangle
    = geometry definition / MeshData creation

GPU layer
    = GPU representation

Renderer
    = rendering
```

---

# 11. Static Geometry Creation

For simple built-in primitives such as Triangle, the current API direction is:

```cpp
Triangle::create()
```

returning:

```cpp
MeshData
```

This gives a clean separation:

```text
Primitive factory
        ↓
    MeshData
        ↓
 GPU upload/resource creation
        ↓
    rendering
```

The primitive does not need to know which graphics API eventually consumes it.

---

# 12. Current Triangle Implementation Direction

The Triangle implementation has been moving toward deriving information from the actual `Vertex` definition rather than duplicating constants.

For example, the current code direction included helpers such as:

```cpp
static constexpr std::size_t positionComponentCount() noexcept
{
    return static_cast<std::size_t>(
        Vertex{}.m_position.size()
    );
}
```

This reflects a broader design principle:

> Avoid duplicating information that can be derived from the actual data type.

The Triangle implementation should use the vertex representation/layout to construct the appropriate MeshData rather than scattering hard-coded assumptions throughout the code.

---

# 13. Fixed Arrays → Vectors

An important current decision is that MeshData is becoming vector-based.

Earlier designs were more fixed-size/static.

The current direction is:

```cpp
std::vector<std::byte>
std::vector<std::uint32_t>
```

rather than fixed-size arrays.

Reason:

The engine should eventually support:

* arbitrary vertex counts
* arbitrary index counts
* different mesh sizes
* dynamically loaded meshes
* generated geometry
* potentially imported assets

A triangle is simply the first use case.

---

# 14. "Weakly Typed" Geometry Philosophy

The project intentionally leans toward a **weakly typed/generic mesh representation**.

This does NOT mean the whole engine should become type-unsafe.

Instead:

```text
High-level geometry
    can be strongly typed

        ↓

MeshData
    generic byte representation

        ↓

VertexLayout
    describes interpretation

        ↓

GPU
    consumes structured attributes
```

This gives flexibility while retaining strong typing at appropriate boundaries.

The important principle is:

> Strong types where they provide semantic value; generic/raw representation where the data must be flexible.

---

# 15. GPU Boundary

One of the major architectural goals is to keep CPU-side geometry separate from actual GPU resources.

For example, conceptually:

```text
CPU:

Triangle
   ↓
MeshData
   ↓
VertexLayout


GPU:

MeshData
   ↓
GPU Buffer
   ↓
Vertex Array / Pipeline state
   ↓
Draw
```

`MeshData` should not itself own an OpenGL buffer.

Likewise, `Triangle` should not know about:

```cpp
glGenBuffers(...)
glBindBuffer(...)
glBufferData(...)
```

Those belong in the GPU/rendering layer.

# 23. Design Principles Going Forward

### 1. Keep ownership obvious

If an object owns data, that should be clear from its type and lifetime.

### 2. Separate description from resource

For example:

```text
MeshData        = describes mesh data
GPU buffer      = owns GPU resource
```

### 3. Avoid API leakage

Geometry should not contain OpenGL calls.

### 4. Prefer value semantics where appropriate

MeshData is fundamentally data.

### 5. Avoid premature abstraction

Do not create generic systems until a real use case demonstrates the need.

### 6. Derive information where possible

Avoid duplicated constants when the information can be obtained from the actual type/layout.

### 7. Keep the engine flexible

MeshData should not assume that every vertex is one particular `Vertex` type.

### 8. Use the triangle as the first vertical slice

A simple triangle should exercise the complete architecture without requiring a large engine.

IMPORTANT — ScopedBinder / VAO-EBO Lesson

We initially used:

ScopedBinder<VertexArray> vao(*this);
ScopedBinder<Buffer> bufferObj(buffer);

inside VertexArray::attachIndexBuffer().

This caused the EBO association with the VAO to be cleared when
ScopedBinder<Buffer> went out of scope.

The result was that the Mesh draw call executed but nothing was rendered.

We changed this to:

ScopedBinder<VertexArray> vao(*this);
buffer.bind();

The EBO is intentionally left associated with the VAO.

This is NOT a resource leak.

OpenGL binding state and C++ resource ownership are separate concepts.

The Buffer object still owns the OpenGL buffer and deletes it in its
destructor. The VAO owns the association with the EBO as part of its
OpenGL state.

Current rule:

- Use ScopedBinder when a binding should be temporary.
- Do not blindly use ScopedBinder for bindings that are intended to
  become persistent state of another OpenGL object.
- In particular, EBO binding must remain associated with the VAO after
  attachIndexBuffer() completes.
